Changelog#

All notable changes to this project are documented here. The format follows Keep a Changelog and the project uses Semantic Versioning. 0.6.0 is the first release on PyPI; 0.1.0 to 0.5.0 were development milestones and were not published.

[0.7.0] - 2026-10-23#

Upgrading from 0.6:

  • The default colors is "module_id", not "similarity". Pass colors="similarity" to keep the 0.6 colors.

  • The default color scheme is "C3 Oklch" in the "vivid" tone, as in the web app (was "C3 Sinebow", "strong"). Pass scheme="C3 Sinebow", tone="strong" to keep the 0.6 colors.

  • alluvial.palette is private. alluvial.SCHEMES is now a tuple of scheme names. For the colors of a scheme, use c3 directly.

  • plot() without ax sizes the figure by its content: a small diagram is about 2 inches tall, not 8.

Added#

  • Plain dicts as networks: alluvial.plot([{"Ann": 1, "Bo": 1, "Cy": 2}, {"Ann": 1, "Bo": 2, "Cy": "2:1"}]). A module is an int, a tree path like "2:1" or a tuple.

  • alluvial.partition(modules, flows=None, *, name=None) for one network with optional flows (normalized to sum to 1) and a name. Module paths make sub-modules: a node’s path is its module’s path plus its position in the module, as in Infomap’s .tree files.

  • pandas DataFrames in long format: alluvial.plot(df) with the columns network, node, module and an optional flow, or alluvial.from_dataframe(df, network=..., node=..., module=..., flow=...) for other column names. pandas stays optional.

  • Without flows, modules are sized and sorted by node count (module_size and sort_modules_by default to "nodes" unless set).

  • color_network chooses the network for colors="nodes", as the web app’s selected network does. The default is the first network.

  • Every public function and class has a usage example in its docstring, run as a doctest, and the API reference links to the capabilities sections that use it.

  • Pull requests get a preview of the docs site.

  • Port base: TS master effb609 (web app and @mapequation/alluvial-diagram 1.17.0, with #64). Since 0.6.0 the engine changed in #60 (types only) and #64 (the default colors); the fixtures are regenerated from it.

Changed#

  • The default colors is "module_id".

  • The default color scheme is "C3 Oklch" in the "vivid" tone, the web app’s new default (TS #64). The default scheme and tone have one source: the TS store, through data/color-schemes.json (generate.mjs --make-data writes default and defaultTone from a new DiagramStore). _palette.DEFAULT_SCHEME and DEFAULT_TONE read it, and the engine store and layout() use them.

  • The examples use Infomap’s functional API, infomap.run(...), whose Result alluvial reads (as it did before). infomap.Infomap objects that have run still work.

  • alluvial.palette is private (alluvial._palette), and alluvial.SCHEMES is a tuple of names.

  • The default figure size follows the content: the height grows with the number of modules in the tallest network (2 to 6 inches), and the width with the number of networks and the labels.

  • hierarchy="outline" draws solid dark gray outlines instead of dots. hierarchy_kw still restyles them.

  • The docs, docstrings and messages use American spelling, like the API.

  • The landing page and README lead with what the package does and show a version of the neuroscience alluvial diagram from Wikipedia (examples/hero.py): synthetic yearly citation networks, partitioned with infomap.run, in which Neurology, Psychology and part of Molecular & cell biology merge into Neuroscience.

Fixed#

  • The README images show on PyPI (absolute URLs) and use the current colors.

[0.6.0] - 2026-10-21#

c3 2 in the web app (TS #47, web app 1.16) and the saved tone and offset (TS #57), ported against TS master. Port base: TS master 60fa1bf (#58); tests/fixtures/provenance.txt records it (ts_repo_head). #59 (4a46b90, license credit only) does not touch the engine.

Upgrading from 0.5:

  • New dependency c3-colors==2.0.1 (the Python port of @mapequation/c3, pinned to the TS lockfile’s version).

  • The C3 schemes (the default "C3 Sinebow" included) are c3 2’s (web app 1.16): other colors, hex strings instead of rgb(). Colorings with the default scheme change color, not geometry. alluvial.palette.C3_SINEBOW follows, and the package data c3-sinebow-512.json is gone (SCHEMES["C3 Sinebow"]).

Added#

  • First release on PyPI (pip install alluvial), from mapequation/alluvial-py, with a docs site at https://mapequation.github.io/alluvial-py (Sphinx: the tutorial and capabilities notebooks and the API reference). CI tests Linux and macOS on Python 3.11 to 3.14 and the lowest direct dependencies, runs the fixture check and the fuzz tests against the TS engine at the provenance commit, and checks TS master weekly for drift. A GitHub release vX.Y.Z publishes to PyPI with trusted publishing.

  • c3 2: tone, offset and coloring by module hierarchy (TS #47, web app 1.16), saved with the diagram (TS #57). Ported against the merged TS master (61b5390; packages/alluvial-diagram identical to PR #57’s 9dd2954); re-checked against 60fa1bf (#58). The C3 schemes are computed by c3-colors 2.0.1, the Python port of @mapequation/c3, pinned to the TS lockfile’s version (tests/test_c3_schemes.py checks the pin, and the TS pnpm-lock.yaml when ALLUVIAL_TS_ROOT is set).

    • alluvial.palette: TONES, DEFAULT_TONE, scheme_colors(name, tone, offset), scheme_is_hue_source, default_scheme_offset, hierarchy_options (TS schemeColors, schemeIsHueSource, defaultSchemeOffset, hierarchyOptions), the new scheme "C3 Oklch" (65 schemes), and the d3 interpolators c3 takes as hue sources (alluvial._d3_interpolators, exact ports of d3-scale-chromatic 3.1 with their color data in data/d3-interpolators.json).

    • DiagramStore(tone=, offset=), selected_tone/selected_offset, set_selected_tone, set_selected_offset, set_selected_scheme resetting the offset, and color_module_hierarchy_in_all_networks (TS colorModuleHierarchyInAllNetworks, same mutation order; a list scheme is taken as c3 seeds).

    • layout(..., tone=, offset=, colors="hierarchy") (validated: ValueError for an unknown tone, TypeError/ ValueError for an offset that is no finite number); save_diagram writes them.

    • Saved diagrams: the diagram block is {saveId, position, numNetworks, colorScheme, colorTone, colorOffset, options}, both keys always written (colorOffset null for c3’s default). Reading warns “ignoring the saved color tone (unknown tone)” / “ignoring the saved color offset (invalid value)”; open_networks restores as TS openNetworks (another saved scheme resets the offset; a saved tone/offset applies when present). In layout, explicit tone/offset win, and an explicit other scheme drops the stored offset.

    • Fixtures: regenerated against that TS tree. Every fixture whose colors come from a C3 scheme changes color strings only (no geometry); saved files gain colorTone/colorOffset. 34 new v3 scenarios (every tone, offsets, C3 Oklch, hierarchy coloring, saved tone/offset and their restore rules, reloadStore), the TS-derived tests/data/ts_c3_schemes.json (every C3 scheme x tone x 6 offsets, interpolator samples, hierarchy() of every scheme), and a c3 fuzz mode (gen.py --c3, -k c3).

Changed#

  • Package metadata: authors mapequation, and the license reads “Copyright (c) 2019-2026 The mapequation authors” like the web app’s (TS #59). The fixture tools look for the TS checkout at ../web/alluvial next to this repo unless ALLUVIAL_TS_ROOT is set. The science module_level=2 test counts layouts instead of timing them (test_module_level_on_science_is_one_layout), so slow CI runners pass.

  • TS #58 (60fa1bf): the TS diagram classes keep their arrays and maps in private fields behind getters, and TreePath is refactored. Each getter returns the container that used to be the public field, so nothing the port mirrors changes: the fixtures regenerated against 60fa1bf are byte-identical (ts_repo_head in provenance.txt moves from 61b5390 to 60fa1bf). The fuzz harness’s highlightLeaves assigned LeafNode.metadata, which is now a getter, and threw on every highlight macro; it defines metadata as an own property instead (every TS reader goes through the getter, so this is faithful).

  • Fuzzer: c3 cases carry an open spec (C3_OPEN_VALUES in tools/ts-fixtures/fuzz/gen.py): the saved colorScheme/colorTone/colorOffset are edited (valid, invalid, null, removed, odd literals) before the open, in both directions (TS-save -> Python-open and Python-save -> TS-open), optionally opened by a store with its own scheme, tone and offset. setSelectedOffset ops can be null; offsets include -0.5, 1e-12 and -3e17. TS writes such huge floats as integer literals (-427299959682199200), so the fuzz test reads TS output with integers beyond 2**53 as doubles, like JSON.parse. v1, v2, v4 and c3 seeds 0-4999 pass, c3 also 5000-9999.

  • Fixtures: 297 (205 v1/v2, 77 v3, 15 v4). New v3 scenarios: multilevel-tree__toneRestore{OddColor,HugeOffset}__ roundTrip, nanpath-json__hierarchyLevel2 (string paths with a non-numeric part, which become NaN: TS c3 keys modules by the joined path, and the port’s one shared NaN keeps its tuple keys equal, so the colors match) and wide-tree__hierarchyLevel2 (see Known issues). tests/data/ts_c3_schemes.json gains hierarchyWide.

Known issues#

  • c3-colors 2.0.1 vs @mapequation/c3 2.0.1: hierarchy() colors a module with many sub-modules (about 40 or more) differently: some sibling colors swap (for 119 sub-modules, 8 of 121 colors with C3 Sinebow, 2 with C3 Oklch). Last-bit differences between Python’s math.hypot/libm and V8’s Math.hypot/trig shift the radii, and the farthest-point sampling in c3’s placeChildren breaks near-ties the other way. colors="hierarchy" (color_module_hierarchy_in_all_networks) inherits it. Not patched around in the port: strict xfail tests (tests/test_c3_schemes.py::test_hierarchy_wide_module_matches_ts, tests/test_v3_fixtures.py wide-tree__hierarchyLevel2) wait for a c3-colors release.

[0.5.0] - not published#

Fix round against the TypeScript worktree py-parity-fixes (branched from d0abf3b); see docs/dev/fix-plan.md. Per work package (WP), the fixture and behavior changes are listed below.

Upgrading from 0.4 (breaking):

  • Python >= 3.11 (WP1).

  • The 2019 saved-diagram format is no longer read (ValueError; use alluvial 0.4 to convert) and alluvial.SavedDiagram/alluvial.io.diagram_json are gone (WP2).

  • save_diagram(networks, path, *, loose=False, **layout_kwargs) writes “alluvial network files” formatVersion 1 (a zip by default, loose files with loose=True, one .json for one network); format, version and timestamp are gone (WP2, WP9).   • A node with a non-finite or missing flow raises ValueError at load (WP4).

  • Engine results change where TS was fixed: stree files lose a phantom level, regrouping 1:2 no longer collapses 10:*, recoloring no longer moves modules, similarity chains that start after the first network get their own colors, and module_level expands in one batch (WP3-WP8). Diagrams of plain inputs without these cases are unchanged.

Changed#

  • WP1, breaking: Python 3.10 is no longer supported (requires-python = ">=3.11"; the 3.10 classifier, the ruff py310 target and the 3.10 CI jobs are gone; the lowest-direct-dependencies CI job runs on 3.11). The web-app bridge, checked against 30 new TypeScript reference scenarios (tests/fixtures/v3, bit for bit, plus byte-identical saved texts) and save/load round trips in the differential fuzzer.

Added#

  • alluvial.read loads a saved web-app diagram (a port of the web app’s converter) and returns a SavedDiagram; layout/plot take it and restore its state (layout options, default color, label font size, palette), as the web app that saved it did (restore_state=False loads it like today’s converter).

  • alluvial.save_diagram(networks, path, format="diagram" | "webapp", **layout_kwargs): the web app’s saveDiagram JSON, byte-identical to TS for the same store state, or one Infomap-JSON file per network with the palette (colors) that today’s web app opens (directory or .zip).

  • JSON top-level colors and per-node color (checkColors, including its index-0 quirk); layout keeps input colors by default when the input carries them.

  • The 64 named color schemes of the web app (alluvial.palette.SCHEMES, SCHEME_GROUPS, get_scheme) and layout(..., scheme=...); the scheme also gives the default highlight_colors.

  • Engine: DiagramStore.check_colors, set_network_name, set_module_name, display settings, schemes by name; alluvial._jscompat.js_json_stringify.

  • Module names of a saved diagram (moduleNames) are restored as the modules’ custom names (with restore_state=True), as the 2019-2021 web app did; ModuleGeometry.name carries them and draw shows a module’s name instead of its leaf names, as the web app’s renderer does. (save_diagram still writes moduleNames: [].)

  • A warning when every node flow is zero, negative or not a number (an empty diagram).

  • Tutorial section “Open in the web app”.

Changed#

  • Warnings point at the caller’s line whether layout, plot, read or save_diagram was called (the stack level is computed, not fixed).

  • layout(..., colors=None) is the default when the input carries colors (a saved diagram, or JSON with colors).

  • JSON "flow": null is read as 0 (what JS arithmetic does with the null that JSON.stringify writes for NaN).

  • Examples and the tutorial use only infomap API that 2.15 does not deprecate and 2.14 supports (the relax rate as the --multilayer-relax-rate flag of Infomap.run, partition facts via alluvial.read(im)).

Fixed (v3 parity review)#

  • A saved diagram whose network name is a number shows it as text, and one without a name (or null) shows no name, as the web app does (it showed the network id); a number network id is accepted.

  • A number node path in Infomap or saved-diagram JSON is a top-level module, as in the web app (it was rejected).

Fixed (release review)#

  • save_diagram refuses a path that does not fit the format: a .zip with format="diagram" (it wrote JSON into the zip name) and a .json with format="webapp" (it made a directory of that name).

  • alluvial.read of a .zip or of a directory says how to read web-app files (extract them, *.json).

[0.2.0] - not published#

The v2 features of the web app, each a port of the store operations it uses, checked against 73 new TypeScript reference scenarios (204 in all, bit for bit) and an extended differential fuzzer.

Added#

  • Sub-modules: layout(..., module_level=2) (an int, or one per network) expands every visible module that has sub-modules, as a deterministic sequence of the web app’s expand operations; expand=[(network, module_id), ...] expands single modules first. ModuleGeometry.level, max_level and order and NetworkGeometry.outlines (OutlineGeometry) describe the hierarchy.

  • draw(..., hierarchy=True) draws the parent modules like the web app: offset gray boxes ("shadow", the default whenever the geometry has outlines) or dotted rounded boxes ("outline"); hierarchy_kw styles them. Labels and network names make room for them.

  • Highlight groups: layout(..., highlight={label: identifiers}) or highlight=callable(NodeInfo) -> label | None, with highlight_colors. It runs the web app’s “color by metadata” operation; AlluvialGeometry.highlight_labels (HighlightLabel) keeps the labels, and layout warns where the web app’s color walk leaves labeled nodes gray.

  • Legends: draw(..., legend=True) and alluvial.legend(ax, other=None, **kwargs) add a legend of the highlight labels above the diagram, inside the axes (the fit makes room for it).

  • Module label lines take their node’s highlight color, as in the web app (draw(label_colors="auto"): for highlight diagrams; True always). ModuleGeometry.name_highlight_indices and name_insignificant carry it.

  • More colorings: colors="layer" and colors="physical_id" for multilayer and state networks.

  • Multilayer splitting: layout(..., split_layers=True) (or one flag per network) and alluvial.read(..., split_layers=True) / alluvial.split_layers(nf) give one network per layer, matched by physical id, as the web app does.

  • Infomap JSON input (-o json files, or the parsed dict) for read, layout and plot.

  • layout(..., ids=[...]) sets the network ids.

  • AlluvialArtists.outlines and AlluvialArtists.legend; outline artists have the gid outline:<network>:<path>.

  • Examples examples/hierarchy.py, examples/highlight.py and examples/multilayer.py.

  • A tutorial notebook, docs/tutorial.ipynb (executed with its outputs, and run by the tests): seeded Infomap runs on a small temporal network, colorings, sub-modules, highlight groups, multilayer networks, reading files, a PDF figure for a paper and restyling artists.

  • Warnings for silent mistakes: state networks matched by state id next to networks matched by node id, a module_level deeper than a network’s module tree, a highlight function that labels no node, and highlight identifiers that match no node (now with examples and a hint at identifier=).

Changed#

  • Colliding network ids (files with the same stem in different folders, or NetworkFiles with the same id) are renamed out, out_2, … instead of raising ValueError.

  • layout(names=...) accepts non-string names such as years (converted with str).

  • Every README snippet now runs when pasted from the root of a source checkout (tested).

  • Clearer errors: layout([]) raises ValueError instead of returning an empty geometry; a missing path raises FileNotFoundError (also without a suffix) and a folder IsADirectoryError; draw raises TypeError for networks instead of a geometry and for a figure or an array of axes; unknown keywords of layout and plot suggest the closest valid name.

  • The draw(module_kw=...) docs note that a hatch needs an edgecolor (the edge is drawn in the face color).

  • alluvial.read() checks that the path exists (FileNotFoundError) and is not a folder (IsADirectoryError) before looking at its suffix. module_level accepts numpy integers and arrays. An expand= module without sub-modules says so in the error, and a module that is not shown says whether its parent must be expanded first or it is already expanded. A JSON dict node with a NaN or infinite flow raises ValueError (it used to give an empty diagram). legend on a diagram whose highlight labels are all gray says so.

  • draw and savefig are much faster for diagrams with thousands of labels (text metrics are cached across fits): for the science example with module_level=2, from about 18 s to 4 s for the first draw and from 8 s to 0.4 s for a following savefig, with identical output.

Fixed (parity with the web app)#

  • layout(highlight=...) also labels a leaf that duplicate identifiers leave in a streamline node outside the module tree; before, it could stay gray where the web app colors it (Network.built_leaf_nodes, fixture dupname-tree__highlight).

  • Splitting two inputs with the same file stem (the same file twice, or a/x.tree and b/x.tree) gave colors="module_id" the single-multilayer-network colors. The second input now gets the id x_2 before splitting (layers x_2_layer1, …), so each file’s layers keep their own original id, as with the web app’s distinct file ids (fixture mlayer-split-twice__colorModuleIds). Their layer ids change from x_layer1_2 to x_2_layer1.

  • Node metadata that is not an object (from JSON input): an array is read by index and length as in the web app (fixtures planted-ftree__arrayMetadata, __arrayLength), and a string, number or true raises the web app’s TypeError in the metadata color operations instead of being skipped.

  • Infomap JSON: a top-level name that is "" or a number is used as given (a number as its JavaScript string), as in the web app; a null entry in layers that the layer-name lookup reaches raises ValueError (the web app throws).

Notes#

  • The saved web-app diagram JSON (networks without nodes) is not read yet; it gets its own error message.

  • Hierarchy shadows are drawn opaque in their color over white; the web app’s mix-blend-mode: difference has no vector equivalent, so where a shadow overlaps a module the module simply covers it.

[0.1.0] - not published#

First release.

Added#

  • alluvial.layout(): a port of the layout engine of the mapequation.org alluvial web app (@mapequation/alluvial-diagram 1.15.0). Module order, sizes, margins, streamlines and colors match the web app; all 128 v1 reference scenarios generated from the TypeScript store match bit for bit, and a differential fuzzer (tests/test_fuzz_parity.py, tools/ts-fixtures) compares the two on random networks and operations.

  • LayoutOptions with the web app’s layout options (height, module width, flow and streamline thresholds, margins, vertical alignment, module size and sort order) and the web app’s coloring (colors="similarity", "module_id" or "nodes").

  • AlluvialGeometry: a frozen, renderer-independent geometry contract (modules, groups, streamlines as path codes or SVG paths, labels) with to_dict() / from_dict(). ModuleGeometry.name_candidates offers renderers more label names than the web app’s lines-per-module rule allows.

  • alluvial.read() for Infomap .tree, .ftree, .clu and *_states.* files and for infomap.Infomap objects or their Result (infomap >= 2.14), including state, multilayer and bipartite networks.

  • matplotlib renderer: alluvial.draw(), alluvial.plot() and alluvial.get_artists(). Labels and limits are refitted at every draw (constrained layout, bbox_inches="tight" and resizing work), overlapping labels lose lines instead of colliding, long labels are truncated, gradient streamlines stay small in PDF/SVG, and every artist has a gid.

  • The web app’s color handling (alluvial.palette), including its 512-color c3-sinebow palette.

Notes#

  • Requires Python >= 3.10 and matplotlib >= 3.7. Reading Infomap objects needs infomap >= 2.14, which requires Python >= 3.11; files written by any infomap version read on every supported Python.

  • Hierarchical sub-modules (expand/regroup), highlight groups and Infomap JSON input are planned for a later version.
